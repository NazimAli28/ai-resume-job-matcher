## 3. Recommended data model

### Application record (fields)
- **Core:** job title, company, company ID/domain, location, remote type (remote/hybrid/onsite), employment type, seniority.
- **Compensation:** salary min/max, currency, pay period, bonus/equity notes.
- **Source:** job URL, board/source enum (LinkedIn, Indeed, company site, referral, recruiter, extension, manual), referrer contact ID, board job ID (for dedupe).
- **Job snapshot:** raw job description text captured at save time (the posting can disappear).
- **Dates:** saved_at, applied_at, last_activity_at, next_action_at, closed_at.
- **Stage:** current stage + immutable stage history (from, to, timestamp, source of change: manual / email / extension).
- **Resume and letter:** resume version ID plus a frozen snapshot (file hash + PDF), cover letter version ID, optional tailoring diff.
- **Contacts:** many-to-many link to contacts with role (recruiter, hiring manager, referrer, interviewer).
- **Interviews:** round, type (phone/technical/onsite/panel), scheduled_at, location/link, outcome, prep notes.
- **Outcome:** rejection reason enum, offer details (base, bonus, equity, deadline), withdrawal reason.
- **Misc:** notes (rich text), tags, priority (1–3), visa/sponsorship flag, custom fields.

### Default pipeline stages
1. **Saved** (interested, not applied)
2. **Preparing** (drafting resume/letter; optional, can be hidden)
3. **Applied**
4. **Screening** (recruiter/HR contact)
5. **Interviewing** (sub-status: round N)
6. **Assessment** (take-home or test)
7. **Offer**
8. **Accepted** (terminal)
9. **Rejected** (terminal; reason required)
10. **Ghosted** (system-suggested after X days no response; terminal)
11. **Withdrawn** (terminal; user-initiated)

Keep stages editable, but ship these as the default. Stages 1–3 and 8–11 must map cleanly to a kanban and to an analytics funnel.

## 4. Gaps and opportunities

1. **Resume-version lock.** Competitors link a resume to a job, but none in the sources clearly freeze the exact file sent. A frozen snapshot per application is a clear differentiator for this product.
2. **Source-to-outcome analytics.** Basic stats exist (Huntr Advanced Insights, Eztrackr statistics), but a funnel by source and by resume version is not clearly offered.
3. **Ghosting detection and nudges.** Reminders are present in some tools, but automatic stale-application detection with suggested follow-up copy looks thin.
4. **Email-driven stage updates.** JobTrackerPro and Trackr show demand, but both are small and not polished. A consented Gmail/Outlook parser with user confirmation is open.
5. **Duplicate detection** across boards and re-posts (same company + title + location) is not mentioned in any source reviewed.
6. **Tracker plus resume tailoring in one flow.** Huntr and Teal bundle this, but at high price points. A cheaper bundled offer is a gap.
7. **Lightweight import.** Most users start in Sheets or Notion. CSV and Notion import is a low-friction onboarding path.
8. **Price.** Pro tiers run $40/mo (Huntr) or $29/mo (Teal monthly). Reviewers repeatedly call them expensive relative to value. Annual pricing is absent at Huntr and Teal, which is a gap.

## 5. Concrete feature suggestions (with rationale)

1. **Frozen resume snapshot per application.** Store the exact PDF and hash at apply time, plus a diff to the base resume. Rationale: answers "which version did I send?", which the tracker is meant to answer.
2. **User-triggered capture from any page** (extension and paste/URL fallback). Parse title, company, location, salary and description, and let the user confirm. Rationale: one-click save is table stakes; fallback keeps it working on unsupported sites.
3. **Stage history with time-in-stage metrics.** Rationale: enables funnel and "where do I stall" analytics.
4. **Stale-application nudges.** After N days with no activity, prompt the user with a follow-up draft and suggest marking "Ghosted". Rationale: reminders are common, but suggested action plus ghosting detection is less so.
5. **Source and resume-version funnel analytics.** Show conversion from Applied → Interview → Offer by source board and by resume version. Rationale: makes the resume-version link useful, not just stored.
6. **Consented email sync** (Gmail/Outlook, read-only scopes) that proposes stage changes for user confirmation. Rationale: matches JobTrackerPro/Trackr direction without auto-changing data.
7. **Duplicate detection** on save (company + title + location, plus board job ID). Rationale: reposts and multi-board listings inflate pipelines.
8. **Calendar sync for interviews** with prep notes attached. Rationale: interviews are the highest-value events; keep them next to the application.
9. **Contacts linked to applications** with a "referral" flag and last-contacted date. Rationale: referrals convert better, and light CRM avoids a separate tool.
10. **CSV / Notion / Sheets import, plus full export.** Rationale: lowers switching cost and signals data ownership.

## 6. Legality and ToS: capturing postings vs scraping

- **LinkedIn.** The User Agreement prohibits scraping. In *hiQ v. LinkedIn* (N.D. Cal., Nov. 2022), the court found hiQ breached the agreement by scraping and using scraped data, but left the CFAA questions open and did not finally resolve the case. Source: https://proskauer.com/blog/court-finds-hiq-breached-linkedins-terms-prohibiting-scraping-but-in-mixed-ruling-declines-to-grant-summary-judgment-to-either-party-as-to-certain-key-issues . Exact §8.2 wording was not retrieved; check the current agreement.
- **Practical distinction.** A user-initiated "clip this page I'm viewing" action is far closer to normal browsing than automated crawling or bulk collection. Automated crawling, background fetches, or bulk harvesting of postings is where ToS and CFAA risk concentrates.
- **Suggested policy for the product:**
  - Capture only on explicit user click, for the page the user is viewing.
  - No headless or background crawling of job boards.
  - Store only what the user saved; do not redistribute postings.
  - Respect robots and board terms; maintain a per-board allow/deny list.
  - Prefer official APIs or partner feeds where they exist.
  - Do not capture other people's personal data beyond what the user needs for contacts; add a deletion path.
- **Email sync** requires OAuth scopes and privacy disclosure (Google API limited-use requirements apply to Gmail scopes).
- **Not legal advice.** Have counsel review the capture and email-sync design before launch.
